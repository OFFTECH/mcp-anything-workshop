# Exercise 01: a CalculiX server for a cantilever beam

You build an MCP server for CalculiX with `/mcp-anything`. At the end, Claude can check a deck against rules you
reviewed, start ccx on it in the background, read the tip displacement and the support reaction from the results, and
compare them with beam theory.

**Before you start:** exercise 00 is done, so the manual is in `~/calculix-manual/2.21/html`. This exercise needs
MCP-Anything with its batch-solver route.

## The materials

| File | What it holds |
|---|---|
| `cantilever.inp` | A steel cantilever, 1000 × 20 × 20 mm, fixed at x = 0, meshed with 40×2×2 C3D20R elements (20-node bricks): 1221 nodes. A load of 21 N in -y at the tip, 1 N on each of the 21 tip nodes. Units N/mm/MPa. Node sets: `FIX` (x = 0), `TIP` (x = 1000) and `TIPC` (the node at the centre of the tip). |
| `reference.json` | Beam theory for this beam: `tip_displacement_y` = -2.5 mm and `support_reaction_y` = 21 N, with their tolerances (2 % for the displacement). |
| `broken/bad_modulus.inp` | The same deck with Young's modulus written as `abc`. |
| `broken/expected.json` | `{"bad_modulus.inp": ["NOT_NUMERIC"]}`: the finding MCP-Anything's deck check must report for that deck. |

The reference comes from P·L³/(3·E·I), with P = 21 N, L = 1000 mm, E = 210000 MPa and I = 20·20³/12 mm⁴: the tip
moves 2.5 mm down, and the support pushes back with 21 N. These files are generated by `python3 -m workshop.generate`:
do not edit them by hand.

## The keywords in the deck

Every keyword, with the section of the CalculiX 2.21 manual that defines it. The rules of your input schema cite the
same sections.

| Keyword | What it does in this deck | Manual |
|---|---|---|
| `*HEADING` | a title line | §7.71 |
| `*NODE` | the 1221 nodes, in the set `NALL` | §7.95 |
| `*ELEMENT` | the 160 elements, `TYPE=C3D20R`, in the set `EALL` | §7.49; C3D20R: §6.2.5; node order: Figure 60 in §6.2.4 |
| `*NSET` | the node sets `FIX`, `TIP` and `TIPC` | §7.100 |
| `*MATERIAL` | the material `STEEL` | §7.83 |
| `*ELASTIC` | E = 210000 MPa, ν = 0.3 | §7.46 |
| `*SOLID SECTION` | the elements of `EALL` are steel | §7.118 |
| `*STEP` | starts the load step | §7.124 |
| `*STATIC` | a linear static analysis | §7.122 |
| `*BOUNDARY` | `FIX` held in directions 1 to 3 | §7.4 |
| `*CLOAD` | 1 N in -y on each node of `TIP` | §7.15 |
| `*NODE PRINT` | the displacement `U` of `TIPC` and the total reaction `RF` of `FIX`, into the `.dat` file | §7.98 |
| `*NODE FILE` | the displacements, into the `.frd` file | §7.96 |
| `*EL FILE` | the stresses, into the `.frd` file | §7.51 |
| `*END STEP` | ends the step | §7.54 |

Two general rules apply too. Units (§3): CalculiX has no units of its own, so a deck must use one consistent set; this
one uses N, mm and MPa. Line length (§5.1): a deck line has at most 132 columns.

**The server does not check these two rules.** The schema of the deck check holds rules for keywords and their data
(which cards, which fields, a number or a name); its format can express neither a unit nor a line length. Expect the
review card in Phase 6 not to list them: ask the agent to note both in DECISIONS.md as "not enforced", and do not ask
it to invent a check for them. That is
fine here: `cantilever.inp` is generated with one set of units, N, mm and MPa, and its longest line has 94 columns. With
a deck of your own, keep to both rules yourself: the server will not warn you.

## What to answer, phase by phase

MCP-Anything asks one or two questions at a time and ends every phase with a card for you to confirm. Answer in your
own words; this section says what matters. Before it runs a check, reads a file or runs ccx, it asks you and says
exactly what it will do.

### Phase 1: the interview

| It asks | You answer |
|---|---|
| Which software, which version, where is it installed? | CalculiX (`ccx`), version 2.21, from the Ubuntu package `calculix-ccx`, installed as `/usr/bin/ccx`; its version flag is `-v`. |
| Walk me through a typical task. | "run a linear static analysis of an .inp deck and read the tip displacement and the support reaction from the .dat file" |
| How long does a run take? Must it keep going after you close Claude Code? | The answer below. It decides the route. |
| What do you have besides the program? | The exercise folder, with an example deck, a broken deck and reference values from beam theory in `reference.json`; and the CalculiX 2.21 manual as HTML pages in `~/calculix-manual/2.21/html`. Give both as absolute paths. |
| What must never happen? | Your choice, for example: "Never change the files in the exercise folder or the manual, and never report a result from a run that failed." |

**The run time (Phase 1, question 3).** This answer decides between a server that waits for each run (`cli`) and one
that starts runs in the background (`batch_solver`). Answer for the work this server is for, not only today's small
deck:

> The workshop decks finish in seconds, but the analyses I build this server for (full cable cross-sections, nonlinear
> and contact runs) take from several minutes to a couple of hours,
> and a run must keep going after I close Claude Code. Plan for runs of up to 2 hours.

MCP-Anything records it as `interview.run_time`. With this answer Phase 3 recommends `batch_solver` (MCP-Anything's
`playbooks/routes/batch-solver.md`, "When it applies"). An answer such as "it runs in seconds" makes it recommend `cli`
instead, and none of the steps below apply. In Phase 6 the answer also sets `[jobs]` `timeout_hours` to about 6:
three times the longest run.

If it asks for a name for the software, "CalculiX" is fine.

### Phase 2: the inventory

The agent lists the read-only checks it would like to run, and runs only the ones you approve.

- **The version.** It proposes `help_output` with the flag `-v` on `/usr/bin/ccx`. Approve it. ccx prints
  `This is Version 2.21` and exits with code 201: that is how ccx 2.21 always ends `-v`, not a failure. Phase 6
  takes `version_exit_codes=(0, 201)` from exactly this evidence.
  If it proposes another version flag, ask for `-v` instead.
- **The command line.** ccx has no help flag, so the inventory card shows ✘ for Command line. That is expected: if the
  agent also plans a help check, you may approve it or leave it out ("Only some of them"), and the card shows ✘ either
  way. Tell the agent the documented command line: `ccx -i <jobname>`, where `<jobname>` is the deck's file name
  without `.inp` (manual §7). It records that as a fact.
- A look at the exercise folder (`sniff_files`) or at the manual folder (`list_docs`, `doc_structure`) only reads:
  approve them if it asks.

Confirm the card when it matches what you told it.

### Phase 3: the route

The route card recommends `batch_solver`: decks in files, result files, the documented `ccx -i <jobname>`, and runs
that can take hours and must keep going without Claude Code. Confirm it.

It recommends `cli`? Then your run-time answer did not come through. Correct it: say again that runs take up to 2 hours
and must keep going after you close Claude Code.

### Phase 4: documentation

If MCP-Anything offers to serve the manual now, answer:

> No documentation for now: I add it in exercise 03 with `/mcp-anything:knowledge`.

It records `knowledge` = `none`, or only the example decks in `inputs/examples/` if it offers to serve those. Either is fine.
With the example decks, the build in Phase 6 also makes their index, and the server gets two more read-only tools,
`search_docs` and `read_section`. The agent still reads the manual pages it cites in the schema (Phase 6), with your
consent.

### Phase 5: the tools

The agent proposes a small set of tools. Expect something like this; the names may differ.

| Tool | What it does |
|---|---|
| `server_status`, `job_status`, `cancel_job` | come with every batch-solver server |
| `validate_deck` | checks a deck against the schema you review, without running ccx |
| `run_analysis` | the core action: starts ccx on a deck from `inputs/`, in the background, and returns a job id |
| `read_results` | reads `tip_displacement_y` and `support_reaction_y` of an ended run from its `.dat` file |
| `compare_to_reference` | compares them with `reference.json` |

Ask for exactly the names `tip_displacement_y` and `support_reaction_y`, as in `reference.json`: any other name makes
the comparison report the value as missing. The displacement is the y-component in the block
`displacements (vx,vy,vz) for set TIPC`. The reaction is the y-component of the total force of the set `FIX`.

Then come three separate questions:

- **Can your program's input files run commands or open other files?** Answer: "Yes: a deck can open other files
  (`*INCLUDE`, and `INPUT=` on a few keywords such as `*RESTART`); it cannot run commands." The agent then adds a guard
  to the run tool that refuses such keywords, with a test for each and one for the real deck, and notes it in
  DECISIONS.md as a best-effort guard. That takes a few minutes; the decks of this workshop use none of these keywords.
- **Turn on starting and cancelling runs** (the core action and `cancel_job`)? Answer "Yes, turn it on": the golden
  check in Phase 7 starts ccx through it. Claude Code still asks you before every run and every cancel.
- **A reduced or test run?** Answer: "None for this server: every run is a full run." It records `smoke_mode` =
  `none`.

### Before Phase 6: may it run ccx?

Answer "Yes, you may run it". Every check of the server runs ccx on each example deck, each broken deck and the golden
deck, as background runs in `outputs/_tests/jobs/`. On this beam each run takes seconds.

### Phase 6: the build

- **The executable** for the scaffold is `/usr/bin/ccx`.
- **`server.toml`:** `[jobs]` `timeout_hours` about 6, `max_running` 1.
- **The version (what to expect).** The agent reads the Phase 2 evidence and sets `version_args=("-v",)` and
  `version_exit_codes=(0, 201)` in `get_backend()`. `server_status` then shows `version` `2.21` and `version_error`
  `None`. If the agent asks how ccx reports its version, give it this same answer: "`ccx -v` prints
  `This is Version 2.21` and exits with code 201; that is its normal end."
- **The decks.** The examples go in `inputs/examples/`: `cantilever.inp`. The broken deck and `expected.json` go in
  `inputs/broken/`: `bad_modulus.inp`, with its entry `"bad_modulus.inp": ["NOT_NUMERIC"]` in
  `inputs/broken/expected.json`, next to the entries for the agent's own broken decks. The agent asks before it copies
  them.
- **The schema.** The agent reads the deck and the manual pages of its keywords (after asking you) and drafts
  `schema/input.json`: one rule per keyword, each citing its manual section. Then it shows the **review card**. Check
  it against the keyword table above:
  - every keyword of the deck has a rule, citing the right section;
  - the data of `*ELASTIC` must be numbers, or `bad_modulus.inp` passes the check and `NOT_NUMERIC` never appears;
  - lines that start with `**` are comments;
  - the card does not list the units rule or the line-length rule: ask the agent to note both in DECISIONS.md as
    "not enforced" (see "The keywords in the deck").

  When it is right, confirm it. The agent records the card's fingerprint as `schema_reviewed`. Every later change of the
  schema shows the card again and needs a new confirmation.
- **The hooks:**
  - `DECK_GLOB` `*.inp`.
  - `CROSSCHECK_MODE` `full`: `smoke` is only for a reduced run that checks the whole deck as a full run does, and this
    server has none.
  - `start_solver` runs `ccx -i <jobname>`, with the deck's name without `.inp`.
  - `solver_accepted`: exit 0; no `*ERROR` and no `Card image cannot be interpreted` in the log; `<jobname>.dat` exists
    and is not empty. The result tool, not the hook, checks that the block it reads
    (`displacements (vx,vy,vz) for set TIPC`) is there, so the same hook also accepts exercise 02's decks.
- **Broken decks.** MCP-Anything also writes broken decks of its own, usually one with an unknown keyword. ccx 2.21
  does not reject an unknown keyword: it prints `*WARNING in calinput. Card image cannot be interpreted` and finishes
  with exit 0. Tell the agent:

  > `solver_accepted` must also refuse a log that contains `Card image cannot be interpreted`.

  Then the cross-check passes for that deck too. `broken/bad_modulus.inp` (`NOT_NUMERIC`) is the broken deck this
  exercise provides: ccx refuses it with an `*ERROR` and exit 201.

While it writes the tools, the agent may ask more questions that nothing above answers:

| It asks | You answer |
|---|---|
| How many cores may a run use? | "One run at a time, with CalculiX's default number of threads. Set no thread count." (`max_running` 1 is the first half of that.) |

### Phase 7: the check

- **The golden check uses `reference.json`.** The agent copies `cantilever.inp` and `reference.json` into
  `inputs/golden/`. The golden test starts the deck with the core action, waits for the run, reads its results, and
  calls `compare_to_reference`, which must report `matches: true`. When it asks where the reference comes from: beam
  theory, with the tolerances in the file.
- The agent then runs MCP-Anything's check until it passes.

### Phase 8: register and try it

- Choose "Only this folder". Restart Claude Code in this folder (`/exit`, then `claude`) and approve the new server
  when asked; `/mcp` shows whether it is connected.
- Try it: "Check the cantilever deck you gave it (it is in the server's `inputs/` folder), run it, and compare its
  results with the `reference.json` you gave it." Claude asks before it starts the run.
- Claude says "not found"? The server looks for a deck by its path inside `inputs/`, and the decks sit in subfolders
  (usually `examples/` and `golden/`). Ask Claude to list `inputs/` and to use the path it finds, for example
  `examples/cantilever.inp`.

## If something goes wrong

| What you see | Why, and what to do |
|---|---|
| The route card recommends `cli` | The run-time answer did not come through: give it again (Phase 1, question 3). |
| `server_status` or a run shows "ccx exited with code 201 when asked for its version" (`BACKEND_FAILED`) | `version_exit_codes=(0, 201)` is missing in `get_backend()`: ask the agent to set it from the Phase 2 evidence. If it cannot, your MCP-Anything is too old: tell the instructor. |
| The cross-check fails on the agent's unknown-keyword deck | `solver_accepted` does not yet refuse `Card image cannot be interpreted`. |
| `/mcp-anything:check` fails at `schema_reviewed` | The schema changed after your review: ask the agent to show the review card again. |

## Done when

- `/mcp-anything:check` passes, and
- a compare reports `matches: true`.

## Discussion

- An unknown keyword only gives `*WARNING in calinput. Card image cannot be interpreted`, so the schema's
  `UNKNOWN_KEYWORD` and `solver_accepted` together protect you: the first refuses such a deck before ccx runs, and the
  second refuses the run if such a deck reaches ccx anyway.
- ccx exits 201 on input errors, as with `bad_modulus.inp`, and also after printing its version. The exit code alone
  cannot tell those apart: the version check needs the version line as well.
- Why does one sentence about run time decide the whole shape of the server?
- Why solid C3D20R elements rather than beam elements? ccx expands every B32R beam element into a 20-node brick
  internally (the `*ELEMENT` section, §7.49, and §6.2.33), so a beam model is solved on nodes you never wrote, and it
  is less clear where its results are reported.
